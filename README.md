# Lifepointe Chiropractic & Wellness Center — website

The website for Lifepointe Chiropractic & Wellness Center in Clarkston, Michigan, plus the
practice's HTML email template. The site is nine static pages generated by a small Python
script. It needs Python 3.9 or newer and nothing else: the build uses only the standard
library, so there is nothing to install.

## Layout

```
build.py           entry point: python3 build.py [--out DIR]
preview.py         serves the built site on this computer, as GitHub Pages does
data/              the site's content as JSON (most edits happen here)
generator/         the generator itself
  main.py          the build: check data, render pages, copy static folders, check output
  data.py          loads data/*.json and stops the build on any problem
  layout.py        shared head, header, footer, page hero and closing CTA band
  pages/           one module per page; prose used on only one page lives here
                   (not_found.py is the 404 page; privacy.py, accessibility.py,
                   nondiscrimination.py and good_faith_estimate.py are the footer's
                   legal pages, see Legal pages)
  seo.py           canonical URLs, link-preview tags, the home page's JSON-LD,
                   sitemap.xml and robots.txt (see Search engines and link previews)
  card.py          the /card redirect behind the business-card QR code (see below)
  hours.py         office-hours table and footer summary
  icons.py         inline SVG icons, by name
  helpers.py       esc(), which escapes every data value placed into HTML,
                   page_href(), which writes a link to a page without .html,
                   mailto() for links that open a new email with the subject and
                   body filled in, and number_word() for counts in running text
  static.py        the folders copied into the site as-is
  checks.py        checks the finished site and the files in email/ for text that
                   must never appear, and the site for stylesheet url()s that name
                   a missing file, for anything a page would load from another
                   site and for links that keep .html or lead nowhere
css/ js/ assets/   stylesheet, script, logos, favicon, photos and web fonts (see Fonts)
email/             standalone HTML email template (see email/README.md); only its images/
                   are published, at /email/images/
forms/             the new-patient intake PDFs, published at /forms/ (see New-patient forms)
DESIGN.md          design system: colors, type, spacing, accessibility floor
dist/             build output (not committed)
.github/           the build-and-deploy workflow and Dependabot settings (see Deploy)
```

## Build and preview

```sh
python3 build.py
python3 preview.py
```

Then open <http://localhost:8000>. `preview.py` serves `dist/` the way GitHub Pages does
(Python's own `http.server` doesn't): `/about` loads `about.html`, and an address with no
page gets `404.html`. Only this computer can connect; Ctrl+C stops it. Each build empties `dist/` and writes it again: the nine
pages, `404.html`, `sitemap.xml`, `robots.txt` and the `/card` redirect, plus copies of `css/`,
`js/`, `assets/`, `email/images/` and `forms/`. The email template itself isn't published: it
is pasted into an email platform, and opening the file previews it.
`--out DIR` builds somewhere else. It uses a new or empty folder, or empties one that an
earlier build made (marked by the empty `.site-build` file each build leaves). It refuses any
other folder. The script works from any directory.

The build stops with a non-zero exit and a message naming the file and field when:

- a data file is not valid JSON, or repeats a key;
- a required field is missing or empty;
- an id is used twice, or a home-page quote names a testimonial that doesn't exist;
- an icon name is unknown, or a menu entry points at a page the build doesn't make;
- a link in the footer's legal row points at a page the build doesn't make (see Legal pages);
- a language-help notice has a bad `lang` tag, `dir` or `edition`, a repeated language, or
  isn't exactly one `{phone}` blank and at most one `{tty}` blank;
- a data value contains HTML markup or an entity;
- a testimonial has a straight `'` or `"`, or is wrapped in quote marks (the page adds its own);
- a success-story category id is already used on that page (`topics`, `topics-h`, `main`,
  `site-nav`, or another category's id or heading id, `<category id>-h`);
- the phone or fax number isn't written like `248-555-0123`, or the phone number shown
  isn't the one dialed;
- the address, fax, dialing number or map coordinates can't be used in the home page's
  JSON-LD, the coordinates don't match the pin in the map link, or the link-preview image is
  missing or a different size (see Search engines and link previews);
- the `/card` redirect would lead nowhere (see Business-card QR code);
- a new-patient form path isn't a PDF in `forms/`, or the file isn't there (see New-patient
  forms);
- the finished site contains any of the text listed in `generator/checks.py`, such as the
  old website's address or a Google Fonts address (see Fonts), or writes the practice's phone
  or fax number any other way than `practice.json` does (such as `248.623.6107` or
  `(248) 623-6107`);
- any text file in `email/` (the template, the signatures, `email/README.md` and the icon
  script) contains that same text, such as the old website's address, its vendor's hosts or
  a banned name, or writes the phone or fax number another way. Only `email/images/` is
  published, but the rest is pasted into email platforms and Gmail, so it is checked where it
  is. No other folder outside the finished site is checked, so notes elsewhere in the
  repository can still name the old website;
- a `url()` in a stylesheet names a file that isn't in the finished site, such as a renamed
  font;
- a page, stylesheet or SVG in the finished site would load anything from another site as it
  opens (a script, image, font, stylesheet, `preconnect`, frame or embed), or a page has a
  form or form field. The privacy policy says neither happens (see Legal pages). Links
  people click, the canonical link and link-preview tags may point anywhere;
- a link on a page to the site's own pages or files ends in `.html`, or leads nowhere: no
  page or file at that address, or no element with the `#section`'s id (see Links). Links
  to other sites aren't checked.

## Links

Every page is a file such as `about.html`, but links leave out the `.html`:
`lifepointechiro.com/about`, `lifepointechiro.com/contact#appointment`. GitHub Pages serves
`about.html` at `/about` (the `.html` address also still works). The code, `data/nav.json`
and `LEGAL_LINKS` name pages by file name; `page_href()` in `generator/helpers.py` writes each
link, and the home page's link is the site's root (`./`, or `/` on the 404 page). A link
written by hand in a page module goes through `page_href()` too; the build stops if one
keeps `.html` or leads nowhere. The canonical URLs, the sitemap, the `/card` redirect and the
email template's buttons use the same form.

## Editing content

| File | What it holds |
|---|---|
| `data/practice.json` | Practice name and legal name, the doctor's name and credentials, phone (`display`, written `248-555-0123`, and the `tel` dialing number), fax (written `248-555-0123`), email, address (`street, city, ST 12345`), map link and the coordinates of its pin (`geo`), social links, recipe book link. `site_url` is the site's own address (`https://` and the domain only). `booking_url` is the online booking page: when it is set, the contact page's appointment section leads with a "Book online" button and the business-card QR code goes there (see below); `null` means the QR code goes to the contact page. `forms` holds the paths of the adult and child new-patient PDFs (see New-patient forms). |
| `data/nav.json` | The header menu, in order. `footer_label` changes an entry's text in the footer's Explore list. |
| `data/hours.json` | Office hours, Monday through Sunday, in 24-hour `HH:MM`. `"hours": []` means closed. This one list feeds both hours tables (home and contact) and the footer summary. |
| `data/services.json` | `home_cards` (home page "What we do"), `services` (services page) and `products`. |
| `data/testimonials.json` | The success stories, by category, in page order. Each category has an `id` (its anchor, as in `success-stories#back-pain`), a `label` (its chip and heading) and its `testimonials`, each with a stable `id` (category id plus the patient's name), the `quote` and the `author`. The success-stories intro counts the categories, so its wording follows this list. |
| `data/home-quotes.json` | The testimonials shown on the home page, as a list of testimonial ids from `testimonials.json`. Each card's label line is its testimonial's category. |
| `data/recipe-staples.json` | Staple ingredients on the recipe book page. |
| `data/team.json` | Staff cards and professional memberships on the about page. |
| `data/language-help.json` | The notice of free language help in each language, word for word from the U.S. Department of Health and Human Services (see Legal pages). Each entry has the language's English `language` name, its `name` in its own script (the footer shows it), its `lang` tag (`es`, `ar`, `zh-Hant`) and `dir` (`ltr`, or `rtl` for Arabic), the `edition` (`2024`, or `2016` where HHS has no 2024 translation), and its `text`, with `{phone}` where the phone number goes and `{tty}` for the relay number (711). |

Rules for data files:

- Write plain text with the real characters (’ “ ” — – … ½), never HTML or entities such as
  `&rsquo;`. The build escapes everything. For a no-break space, type the U+00A0 character
  itself, or write the JSON escape `\u00a0`.
- The order of every list is the order on the page. Nothing is sorted.
- Icon names are the keys of `ICONS` in `generator/icons.py`.
- Keep the practice's own wording and fix typos only. Don't add claims, statistics, reviews,
  testimonials or quotes the practice didn't write.
- Testimonials are the patients' exact words, typos fixed. Leave out the quote marks around
  them, since the page adds its own, and use ’ “ ” for apostrophes and quotes inside them. Leave
  out any testimonial that names former staff. Never edit one to make it fit.

Text that appears on only one page and needs markup (links, emphasis, line breaks) lives in
that page's module in `generator/pages/`. The shared header, footer and CTA band are in
`generator/layout.py`, the styling in `css/site.css`, and the behavior in `js/site.js`.

To add a page, create a module in `generator/pages/` with a `FILENAME` and a `render(site)`
function, add it to `PAGES` in `generator/pages/__init__.py`, and add a menu entry to
`data/nav.json` if it belongs in the menu. Every page in `PAGES` gets a canonical URL and
link-preview tags and is listed in `sitemap.xml`; nothing else needs changing.

## New-patient forms

The home and new-patients pages link to two fillable PDFs in `forms/`:
`new-patient-adult.pdf` and `new-patient-child.pdf`. They are the practice's intake forms,
copied in unchanged. `forms` in `data/practice.json` gives their paths, relative to the
pages, so the links work on any address the site is served from.

To update a form, replace the file and keep its name, so the links stay the same. Check the
new file before committing it: its fields should still fill in, and they should all be blank,
because anything saved in the file is published to everyone who downloads it. The build's
banned-word check (`generator/checks.py`) can't read PDFs, so also check the new file's text
for those words. The accessibility statement says the site meets WCAG 2.1 AA (see Legal
pages), so a new form should too: tagged, with its language and title set, and a tooltip on
every field (in LibreOffice, each control's Help text), which is what screen readers announce.

## Legal pages

Every page's footer links to `privacy.html`, `accessibility.html`, `nondiscrimination.html` and
`good-faith-estimate.html` (`LEGAL_LINKS` in `generator/layout.py`). Their text is in
`generator/pages/`; the phone, email and address come from `data/practice.json`.

- **The nondiscrimination notice is required.** The practice bills Medicare, so Section 1557
  of the Affordable Care Act applies: a notice of nondiscrimination (45 CFR 92.10) and a
  notice of free language help and auxiliary aids in English and Michigan's 15 most common
  other languages (92.11) must be at a conspicuous place on the website. Every footer links
  to the page and lists the languages in their own scripts, each linked to its notice. The
  translations in `data/language-help.json` are HHS's own: copy any change from HHS word for
  word, never machine-translate. The languages are HHS's list for Michigan (August 2016):
  Spanish, Arabic, Chinese (both scripts), Syriac, Vietnamese, Albanian, Korean, Bengali,
  Polish, German, Italian, Japanese, Russian, Serbo-Croatian and Tagalog. HHS's 2024
  translations mention free language help and free aids; it has none for Syriac (it
  translated Assyrian) or Serbo-Croatian, so those two are its 2016 versions, which mention
  language help only. With fewer than 15 employees the practice needs no named coordinator
  or grievance procedure, so the notice names the office.
- **Printing that page gives the office poster.** The rules also want both notices posted in
  the office in at least 20-point sans-serif type. `css/site.css` ("Printed notice") prints
  only the notice, black on white, at 20pt and up. The language notice must also go on intake
  forms and the Notice of Privacy Practices, among other papers (92.11(c)(5)).

- **The Good Faith Estimate notice is required.** Under the No Surprises Act, a provider must
  display information about uninsured and self-pay patients' right to a Good Faith Estimate
  prominently on its website, where search engines can find it, as well as in the office and
  wherever people schedule or ask about costs (45 CFR 149.610(b)(1)(iii)). The page is the
  CMS standard notice word for word (April 2022); only its last paragraph, how to ask this
  office, is the practice's own. If CMS revises its notice, copy the new text exactly. The new
  patients page's insurance card links to it too.
- **Keep the privacy policy true.** It says the site sets no cookies, has no analytics,
  tracking or forms, loads nothing on its pages from other sites and is hosted on GitHub
  Pages, and it names the services the pages link to: Facebook, Instagram, Google Maps and
  Google Drive. Before adding an embed, a script, font or image from another site, a form,
  analytics, a new host or a link to another service, update the policy and its
  `LAST_UPDATED` date. Setting `booking_url` adds "our online booking service" to the policy's
  list of other sites by itself; still update its date, and add a link to the booking
  service's own privacy policy. The build holds the pages to part of this: it stops if one
  would load anything from another site, or has a form (see Build and preview). It can't see
  what a script does once it runs, so check any new script by hand. The legal pages also link
  to GitHub's documentation and privacy statement, the Meta and Google privacy policies and
  the W3C's WCAG 2.1, and the Good Faith Estimate page links to CMS; those are plain links and
  load nothing.
- **Keep the accessibility statement true.** It says the website meets WCAG 2.1 Level AA, so
  keep every page and the new-patient forms to that standard. Its "What the site does" list
  restates the accessibility floor in DESIGN.md. If the floor changes, update the statement and
  its `LAST_REVIEWED` date.
- **The Notice of Privacy Practices is a placeholder.** The privacy policy's last section
  (`#notice-of-privacy-practices`) only says what the notice is and how to ask for a copy.
  Replace it with the practice's own notice, on that page or as a linked file. A covered
  entity with a website must post its notice prominently on it (45 CFR 164.520(c)(3)(i)).

## Fonts

The site's typefaces are served from `assets/fonts/`, so its pages send no request to
Google or any other font service. The `@font-face` rules are at the top of `css/site.css`.
The build stops if any published file names `fonts.googleapis.com` or `fonts.gstatic.com`,
so Google Fonts can't come back unnoticed, and if a `url()` in the stylesheet names a font
file that isn't there. The email template isn't part of the published site (see
`email/README.md`).

- **Bricolage Grotesque** (headings, weights 700 and 800) and **Lato** (body, 400 and 700),
  no italics. These are the woff2 files Google Fonts served in October 2026 for
  `family=Bricolage+Grotesque:wght@700;800&family=Lato:wght@400;700`, unchanged and renamed.
  Bricolage Grotesque is a variable font, so one file covers both of its weights.
- Each typeface is split into character sets (latin, latin-ext and, for Bricolage
  Grotesque, vietnamese), and each rule's `unicode-range` lists its file's characters. A
  browser downloads a file only when the page uses one of those characters, so the English
  pages load just the three latin files, 88 KB, plus the 14 KB Syriac file for the footer's
  language list. The eight files total 140 KB.
- The licenses are `OFL-lato.txt` and `OFL-bricolagegrotesque.txt` in `assets/fonts/`
  (SIL Open Font License 1.1, which allows self-hosting). Keep them next to the fonts.
- To add a Lato weight or style, request the CSS from
  `https://fonts.googleapis.com/css2?family=...` with a desktop Chrome user agent, so that it
  lists woff2 files. Download every file it lists into `assets/fonts/`, then copy its rules
  into `css/site.css` with the `url()` changed to `../assets/fonts/<file>` and
  `font-display: swap` kept. The Bricolage Grotesque files already contain weights 200 to
  800: for another weight in that range, widen the `font-weight` range in its three rules.
- **Noto Sans Syriac Eastern** draws the Assyrian notice of free language help and its name
  in the footer, because many phones have no Syriac font. It is Google Fonts' "syriac" file
  (14 KB, weight 400), with its `unicode-range` cut to the Syriac blocks so it never draws
  Arabic. Browsers download it on any page, since every footer names the language. License:
  `OFL-notosanssyriaceastern.txt`.
- The `/card` redirect loads no fonts: it shows for a moment at most.

## Search engines and link previews

All of this is built from `site_url` in `data/practice.json`, in `generator/seo.py`.

- **Canonical URLs** are `https://lifepointechiro.com/` for the home page and
  `https://lifepointechiro.com/<page>` (no `.html`) for the others, the same form as the
  site's own links (see Links). GitHub Pages also answers `/about.html`; the canonical link
  tells search engines which address to list. Each page also has Open Graph and Twitter card tags, so a
  shared link shows the page's title and description with the practice's logo.
- **JSON-LD.** The home page describes the practice for search engines as a schema.org
  `MedicalBusiness`: name, address, phone, fax, email, map coordinates and link, office hours
  (from `data/hours.json`) and the Facebook and Instagram pages. schema.org has no
  chiropractic type. Its more specific medical types are other specialties, or facilities such
  as `MedicalClinic` (a hospital-style clinic) and `Pharmacy`. `geo` is the pin in `maps_url`
  (the numbers after `!3d` and `!4d`); if the map link changes, update `geo` with it, and the
  build stops if they disagree. Once the site is live, check it by entering
  `https://lifepointechiro.com/` in Google's Rich Results Test.
- **The link-preview image** is `assets/logo-share.png`, set in `generator/seo.py` with its
  width and height; the JSON-LD uses it too. It is `assets/logo-full-color.svg`, 580px wide,
  centered on a white 1200×630 PNG (link previews don't show SVG), so it stays whole when an
  app crops the preview to a square. The build stops if the file is missing or its size has
  changed. Facebook keeps an old preview for a while; its Sharing Debugger fetches a new one.
- **`sitemap.xml`** lists every page in `PAGES`. **`robots.txt`** lets search engines crawl
  everything and gives the sitemap's address.
- **`404.html`** is the page GitHub Pages shows, with status 404, for any address that
  doesn't exist. It keeps the header and footer, asks search engines not to index it and
  isn't in the sitemap. Pages serves it at the missing address itself, at any depth, so its
  links start with `/`, like the `/card` page's. On the temporary
  `rramboer.github.io/lifepointe/` address it therefore shows without styles; test it on
  `lifepointechiro.com` or in `preview.py`, which serves it for any missing address too.

## Business-card QR code (/card)

The QR code on the printed business card opens exactly `https://lifepointechiro.com/card`.
Printed cards last for years, so that address must always work.

- The build writes a small page to `card.html`, like every other page. GitHub Pages answers
  `/card` from it, the same way `/about` loads `about.html`, so the printed address works as it
  is. **Never delete or rename it.** The page is only for the QR code: it isn't in the menu,
  nothing on the site links to it, and it asks search engines not to index it.
- It sends people on at once, with a meta refresh that works without JavaScript and a script
  that does the same. If neither runs, it shows the logo and a button to the same place. It
  loads nothing from other sites.
- **To change where it goes, set `booking_url`** in `data/practice.json` to a full `https://`
  address, such as the online booking page once there is one. That also adds a "Book online"
  button to the contact page's appointment section. While `booking_url` is `null`,
  it goes to the contact page's appointment section, `/contact#appointment`, so keep
  `id="appointment"` on that section; the build stops if it is gone. The page itself is
  `generator/card.py`, and no other page may use the file name `card.html`.
- Its links start with `/`, so they only work at the root of a domain. On the temporary
  `rramboer.github.io/lifepointe/` address it redirects to a page that doesn't exist; test it
  on `lifepointechiro.com`, or at `/card` in `preview.py`.
- After changing it, open `/card` on the live site on a phone, and scan a printed card.

## Deploy

GitHub Actions builds the site and publishes it to GitHub Pages. Generated HTML is never
committed. The workflow is `.github/workflows/deploy.yml`.

- **Every push to `main`**, including a merged pull request, runs `python3 build.py` and
  deploys `dist/`. Runs on `main` take turns: each one builds and deploys before the next
  starts, and none is cut off midway. If several merges land close together, a newer waiting
  run replaces an older waiting one, so the newest commit deploys last. If the live site ever
  lags behind `main`, rebuild by hand (below).
- **Every pull request** runs the same build and attaches the finished site to the run as a
  downloadable artifact named `github-pages`, kept for 14 days. A new push to the pull request
  cancels its older run. To preview it, open the run from the pull request's checks, download
  `github-pages` from the run's summary page, and unzip it outside the repository folder (for
  example in Downloads, so the built pages can't be committed by mistake). Then, in that
  folder, unpack the `artifact.tar` inside and serve it to this computer only, with
  `preview.py` from your copy of the repository:

  ```sh
  mkdir preview && python3 -c "import tarfile; tarfile.open('artifact.tar').extractall('preview', filter='data')"
  python3 path/to/lifepointe/preview.py preview
  ```

  Only preview pull requests opened by you or a collaborator you trust: a pull request from a
  fork runs its own copy of the workflow, so its artifact can contain anything. The `data`
  filter refuses links and paths that lead outside `preview/`, which plain `tar -xf` would
  unpack and the server would then hand to the page. The filter needs Python 3.12 or newer
  (3.9 to 3.11 have it from 3.9.17, 3.10.12 and 3.11.4); older versions stop with an error
  and unpack nothing.

- **If the build fails, nothing deploys** and the last good site stays live. The run's log
  shows the same message as a local build.
- **To rebuild by hand**, use Actions > Build and deploy site > Run workflow. On `main` it
  builds and deploys; on any other branch it only builds.

The upload leaves out hidden files, such as the `.site-build` marker.

Repository settings:

- **Settings > Pages > Source** must be **GitHub Actions**. With "Deploy from a branch", Pages
  would publish the repository's source files (README and all) instead of the built site.
- **Settings > Pages > Custom domain** holds the domain. With the GitHub Actions source, a
  `CNAME` file in the repository is ignored, so don't add one. Verify the domain first, under your
  GitHub profile's Settings > Pages, so no other account can use it, and tick **Enforce
  HTTPS** once GitHub has issued the certificate.
- **Settings > Environments > github-pages > Deployment branches** should allow only `main`.
  Remove any other branch, such as `gh-pages`: a branch the environment allows could deploy
  with an edited copy of the workflow.
- **Settings > Actions > General**: turn on **Require actions to be pinned to a full-length
  commit SHA**, so an edit that adds an unpinned action fails instead of running.

Every action in the workflow is pinned to a full commit SHA, with its version in a comment.
Dependabot (`.github/dependabot.yml`) checks for new versions weekly, waits until a release has
been out for 7 days, and opens one pull request with that week's updates. Its build checks the
new versions of the build actions. The deploy action only runs after merging, so after merging
an update that changes `deploy-pages`, check that the next deploy succeeded.
